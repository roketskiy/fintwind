问题根因是当前退出流程的所有权边界不够强：`fintwind-daemon.exe` 被强制结束时，Windows 不会自动回收其后代进程；而 OpenCode 的 `taskkill /T` 清理逻辑在守护进程内部，守护进程被提前终止就无法执行它。GPUI 对所有退出回调又只有约 200ms 的总等待预算，现有 1 秒守护进程停止流程无法作为可靠保证。

1. 在 `fintwind-client` 的 Windows 专属依赖中启用 Job Object 所需的 `windows-sys` API，并在 `DaemonProcess` 中持有一个 Windows Job Object 句柄。

2. 本地启动 `fintwind-daemon.exe` 后，将其加入配置为 `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` 的 Job Object。Windows 会让子孙进程继承同一个 job，因此 `fintwind-daemon.exe -> opencode2.cmd/cmd.exe -> Bun` 整棵树都受桌面进程所持句柄约束。无论正常协议关闭、退出回调超时、崩溃还是强制结束桌面进程，句柄关闭都会由系统回收后端树。

3. 保留现有的正常退出逻辑：应用真正退出时仍发送 daemon shutdown，让守护进程有机会按正常顺序释放会话和关闭 OpenCode；Job Object 只作为不依赖 GPUI 等待时长的可靠兜底。外部 `FINTWIND_DAEMON_ADDRESS` 连接不会创建或关闭本地 Job，不影响外部托管服务。

4. 合并当前三个 `on_app_quit` 回调为一个有顺序的回调：先保存草稿与应用状态，再启动 daemon shutdown。现有回调在 GPUI 中是并发等待的，导致草稿保存可能与 daemon 停止竞争。这会恢复“退出前持久化”的原有语义。

5. 增加 Windows 专属的 Job Object 单元测试，验证将子进程加入 kill-on-close job 后关闭 job 会结束其进程；同时保留跨平台 client 测试。最后构建默认 `target/release` 二进制，并通过真实启动 OpenCode 会话、退出应用、检查 Bun 进程是否消失进行验证。
